# DuckLog (덕로그)

## 1. 서비스 소개

덕질(아이돌, 뮤지컬, 스포츠 직관, 굿즈 수집 등) 기록을 남기고, 그 기록을 모아 실물 포토북으로 주문·제작할 수 있는 개인용 웹 서비스입니다.

- **타겟 사용자**: 좋아하는 아이돌·뮤지컬·팀 등을 응원하며 사진과 짧은 글로 매일의 순간을 기록하고, 나중에 그 기록들을 실물 책으로 간직하고 싶은 팬덤/취미 활동자.
- **주요 기능**
  - 카테고리별(아이돌/뮤지컬/스포츠/굿즈/후기) 덕질 기록 작성·조회·수정·삭제
  - 기록마다 **DC 스타일 / 후기 스타일 / 다이어리 스타일** 중 원하는 표시 디자인을 골라서 작성 (스타일에 따라 부제·좌석·평점·태그 같은 전용 입력 항목이 나타남)
  - 홈 화면에서 캘린더 뷰 / 피드 뷰로 기록 훑어보기, "기록 모아보기" 화면에서 카테고리별 필터링
  - 포토카드 갤러리 등록·관리 (다중 업로드, 카드에 보여질 사진 위치 직접 드래그로 조절)
  - 기록·포토카드를 골라 실제 책 페이지를 펼쳐보며 드래그(또는 모바일 탭)로 배치하는 4단계 포토북 제작 마법사
  - 완성된 책 주문 접수, 마이페이지에서 진행 상황 확인 및 대기중 주문 취소
  - 관리자 페이지에서 전체 주문 관리(상태 변경, 삭제, JSON/CSV 내보내기)

## 2. 실행 방법 (Docker)

**Node.js나 PostgreSQL을 컴퓨터에 직접 설치할 필요가 없습니다.** Docker만 설치되어 있으면 Windows·Mac·Linux 어떤 컴퓨터에서든 아래 명령어 4줄로 동일하게 실행됩니다.

### 준비물

- **Docker Desktop** (Windows/Mac) 또는 **Docker Engine + Docker Compose** (Linux) — [docker.com](https://www.docker.com/products/docker-desktop/)에서 설치 후 실행해두세요.
- **Git**

### 실행

```bash
# 1. 저장소 클론
git clone <repo-url>
cd DuckLog

# 2. 환경변수 파일 준비 (최초 1회만)
cp .env.example .env

# 3. 실행 (Docker가 이미지 빌드 + DB 기동 + 서버 시작까지 전부 처리합니다)
docker-compose up

# 4. 브라우저에서 접속
http://localhost:3000
```

> Docker Compose 최신 버전을 쓴다면 `docker-compose up` 대신 `docker compose up`(하이픈 없이, `docker` 뒤에 공백)도 동일하게 동작합니다.

첫 실행은 이미지 빌드와 패키지 설치 때문에 1~2분 정도 걸릴 수 있습니다. 이후에는 `docker-compose up`만으로 바로 뜨고, **코드를 직접 수정한 경우에만** `docker-compose up --build`로 다시 빌드해주면 됩니다.

### 포트가 이미 사용 중이라면

기본 포트는 App `3000`, DB `5432`입니다. 다른 프로그램이 이미 그 포트를 쓰고 있다면 `.env` 파일만 열어서 숫자를 바꾸면 됩니다 (`docker-compose.yml`은 건드릴 필요 없음).

```bash
# .env
APP_PORT=4000
DB_PORT=5433
```

```bash
docker-compose up
# http://localhost:4000 으로 접속
```

### 자주 있는 문제

- **`.env` 값을 바꿨는데 반영이 안 돼요** → `docker-compose restart`가 아니라 완전히 내렸다 올려야 합니다: `docker-compose down` 후 `docker-compose up`.
- **포트 충돌 에러가 나요** → 위의 "포트가 이미 사용 중이라면" 항목대로 `.env`의 포트 번호를 바꿔주세요.
- **Docker Desktop이 실행 중인지 확인** (Windows/Mac) → 작업표시줄/메뉴바에 고래 아이콘이 떠 있어야 정상 동작합니다.

### 종료

```bash
docker-compose down       # 컨테이너만 정리 (작성한 기록은 보존됨)
docker-compose down -v    # DB 데이터까지 완전히 삭제
```

## 3. 완성한 레벨

- **Lv1 — 덕질 기록 작성/관리**
  - 카테고리별(아이돌/뮤지컬/스포츠/굿즈/후기) 기록 작성 폼: 말머리(카테고리) + 제목 + 리치텍스트 에디터(굵게/기울임/정렬/링크/이미지 삽입) + 이미지 첨부
  - 기록 목록/상세/수정/삭제 전체 CRUD
  - 홈 화면에서 캘린더 뷰 / 피드 뷰 전환, 하루에 기록이 여러 개인 날짜는 별도 목록 페이지로 분기
  - "기록 모아보기" 화면에서 전체/카테고리별 필터링
- **Lv2 — 포토북 주문**
  - 기록 선택 → 포토카드 선택 → 책 구성하기 → 미리보기, 4단계 마법사로 책을 만들고 주문 접수
  - 관리자 페이지에서 전체 주문 조회, 상태(대기중→처리중→완료) 변경, 삭제, JSON/CSV 내보내기
  - 마이페이지에서 내 주문 현황 확인, 상세페이지 이동, 대기중 주문 취소(확인창 포함)
- **Lv3 — 추가로 고도화한 부분**
  - **책 만들기 편집기**: 책 구성하기 단계를 실제 펼침면(양쪽 페이지) UI로 재현. 책은 빈 페이지에서 시작해서 기록·포토카드를 원하는 자리로 드래그(모바일에서는 탭 → 탭으로 배치)해서 채우고, 포토카드 여러 장은 한 페이지에 병합/분리 가능. 페이지 내용은 잘리지 않도록 자동으로 축소해 맞추는 스케일-투-핏 처리 적용
  - **게시물 표시 스타일 3종**: 같은 글도 DC 스타일(단순 카드형) / 후기 스타일(콘서트 로그풍 배너+하이라이트) / 다이어리 스타일(스크랩북풍 평점·태그·메모) 중 골라서 보여줄 수 있고, 스타일별 전용 입력 항목이 작성 폼에 나타남. 상세페이지에서 제목/부제 등 핵심 항목은 바로 클릭해서 인라인 편집 가능
  - **포토카드 갤러리**: 다중 업로드 지원, 업로드한 사진에서 카드에 보여질 부분을 직접 드래그로 지정하는 위치 조절 팝업
  - **모바일 대응**: 터치에서 동작하지 않는 네이티브 드래그 앤 드롭을 대체하는 탭-투-플레이스 인터랙션, 좁은 화면에서 양페이지 미리보기가 위아래로 쌓이는 반응형 레이아웃

## 4. 사용자 경험(UI/UX) 설계

- **타겟 사용자**: 특정 아이돌/그룹, 뮤지컬, 스포츠 팀 등을 응원하는 팬. 콘서트·팬미팅·직관 후기를 그때그때 짧게 남기고, 연말이나 기념일에 모아서 실물 책으로 소장하고 싶어하는 사람을 가정했습니다.
- **화면·흐름 판단**
  - 글쓰기 화면은 팬 커뮤니티에서 익숙한 "말머리 + 제목 + 리치텍스트 본문" 형태로 통일해, 카테고리마다 입력 항목이 달라지는 복잡한 폼 대신 누구나 바로 쓸 수 있게 했습니다. 대신 "어떤 디자인으로 보여줄지"는 스타일 선택으로 분리해서, 원할 때만 후기/다이어리 스타일의 추가 입력(평점, 태그 등)을 열어볼 수 있게 했습니다.
  - 책 만들기는 "무엇을 넣을지"와 "어떻게 배치할지"를 한 화면에서 동시에 결정하게 하지 않고, 선택(기록) → 선택(포토카드) → 배치 → 미리보기로 단계를 쪼개 한 번에 내려야 하는 판단을 줄였습니다.
  - 배치 단계에서 실제로 인쇄될 페이지 모양 그대로 보여주는 편집기를 만들어, 주문 전에 완성본이 어떻게 나올지 불안해하지 않도록 했습니다.
- **의도적으로 넣지 않은 것**
  - 회원가입/로그인 및 다중 사용자 인증 — 개인이 자신의 기록을 남기는 1인용 앱으로 설계해, 모든 요청이 하나의 데모 사용자로 동작합니다. 관리자 페이지도 별도 인증 없이 열려 있습니다.
  - 실제 결제 연동 — 주문은 상태 추적(대기중/처리중/완료)까지만 다루고, 결제/배송 단계는 범위에서 제외했습니다.
- **주요 화면**: 홈(캘린더·피드), 기록 작성/상세(스타일 3종), 포토카드 갤러리, 책 만들기 4단계 마법사, 마이페이지, 관리자 페이지. _(스크린샷은 추후 `docs/screenshots/`에 추가할 예정입니다.)_

## 5. 기술 스택 및 아키텍처

| 영역 | 선택 | 왜 선택했는지 |
| --- | --- | --- |
| 프레임워크 | **Next.js 14 (App Router)** | 화면(React)과 API(Route Handler)를 같은 프로젝트, 같은 언어로 함께 짤 수 있어서 별도의 백엔드 서버를 새로 구축할 필요가 없었습니다. 페이지는 서버에서 미리 렌더링되고, 필요한 부분만 클라이언트 컴포넌트로 인터랙션(드래그, 폼 입력 등)을 처리하는 식으로 나눠 썼습니다. |
| 언어 | **TypeScript** | `Post.category`, `BookPage` 같은 데이터 모양을 타입으로 고정해두면, 필드 이름 오타나 다른 형태의 값을 실수로 넣는 걸 저장하기 전에 바로 잡아낼 수 있습니다. 특히 이번 프로젝트처럼 AI와 대화하며 반복적으로 코드를 고치는 방식에서는, 타입 에러가 "여기 잘못됐다"를 즉시 알려줘서 검증 속도가 빨라집니다. |
| 스타일 | **Tailwind CSS** + 커스텀 디자인 토큰 | 별도 CSS 파일을 만들지 않고 클래스 조합만으로 웜톤 스크랩북/폴라로이드 감성의 커스텀 디자인(색상, 폰트, 그림자 등)을 빠르게 구현할 수 있었습니다. `Libre Caslon Text`/`Source Serif 4`/`Bricolage Grotesque`/`Noto Serif KR` 등 폰트도 프로젝트 전용 토큰으로 등록해서 재사용했습니다. |
| DB | **PostgreSQL 15** | 이미지 URL 목록(`images: String[]`), 책 페이지 배치(`pages: Json`), 스타일별 메타데이터(`metadata: Json`)처럼 구조가 유동적인 데이터를 배열·JSON 타입으로 그대로 저장할 수 있어서, 스타일이 늘어나거나(DC/후기/다이어리) 기능이 추가돼도 스키마를 크게 바꾸지 않아도 됐습니다. |
| ORM | **Prisma** | `schema.prisma` 파일 하나로 테이블 구조를 코드처럼 관리하고, `prisma db push`로 컨테이너가 켜질 때마다 DB에 즉시 반영되게 했습니다. 버전 관리되는 마이그레이션 파일 대신 이 방식을 쓴 이유는, 혼자 개발하면서 스키마를 자주 바꾸는 단계에서는 마이그레이션 파일을 쌓는 것보다 "지금 스키마 그대로 반영"이 훨씬 빠르고 단순하기 때문입니다. |
| 인프라 | **Docker Compose** (`app` + `db` 2개 컨테이너) | Node.js나 PostgreSQL 버전 차이로 "내 컴퓨터에서는 되는데" 문제가 생기지 않도록, 실행 환경 자체를 컨테이너로 고정했습니다. 덕분에 Windows에서 개발한 것을 다른 컴퓨터에서도 `docker-compose up` 한 줄로 동일하게 재현할 수 있습니다. 포트도 `.env`로 오버라이드할 수 있게 해서, 다른 프로그램과 포트가 겹쳐도 코드를 안 건드리고 해결되게 했습니다. |
| 인증/사용자 모델 | 로그인 없는 **단일 데모 사용자** (`lib/current-user.ts`) | 여러 사람이 함께 쓰는 서비스가 아니라 "나만의 덕질 다이어리"라는 컨셉이라, 회원가입/로그인 흐름을 걷어내고 모든 요청이 하나의 사용자로 동작하도록 단순화했습니다. 덕분에 회원 인증 관련 코드 없이 핵심 기능(기록 → 포토북)에 집중할 수 있었습니다. |

**디렉터리 구조**

```

  book-preview.tsx        책 완성본 양페이지 미리보기
  photocard-position-picker.tsx  포토카드 위치 조절 팝업
  calendar-view.tsx / feed-view.tsx  홈 화면 두 가지 보기 모드
lib/                도메인 로직/유틸
  category.ts / post-style.ts   카테고리·스타일 라벨 정의
  post-metadata.ts               스타일별 메타데이터 타입
  book-pages.ts                  책 페이지 배치 데이터 모델
  use-scale-to-fit.ts            내용이 잘리지 않게 자동 축소하는 훅

prisma/             schema.prisma (스키마 정의)
```

## 6. AI 도구 사용 내역

이 프로젝트는 기획은 **Gemini**와 대화하며 진행했고, 구현은 **Antigravity**와 **Claude Code**(Anthropic의 AI 코딩 에이전트)를 사용했습니다. 웹앱의 UI 스타일은 **Stitch**로 만든 디자인 시안을 참고해 구현했습니다.

- **Claude Code 활용 방식**: 기능 단위로 한국어 자연어 요청 → AI가 코드를 작성/수정 → Docker 컨테이너 로그와 `curl`로 실제 컴파일·API 동작을 검증 → 테스트 데이터 정리, 순서로 반복했습니다.
- **좋았던 점**: 아이디어를 말로 설명하면 바로 동작하는 화면까지 나와서 반복 실험 속도가 빨랐고, Docker/Prisma 관련 오류(마이그레이션 실패, `.env` 미반영 등)도 원인을 짚어가며 함께 디버깅할 수 있었습니다.
- **아쉬웠던 점**: 요구사항을 짧게만 전달하면 AI가 필요 이상으로 범위를 넓혀 구현하는 경우가 있었습니다(예: 요청하지 않은 관리자 로그인 시스템을 통째로 만들었다가 다시 제거). 구체적으로 범위를 짚어줄수록 의도한 결과에 가까웠습니다. 또한 드래그 앤 드롭처럼 브라우저에서 직접 조작해봐야 알 수 있는 인터랙션은 AI가 스스로 확인할 수 없어, 실제 화면에서 사람이 확인하며 보완하는 과정이 필요했습니다.

## 7. 설계 의도

- **왜 이 서비스 아이디어를 선택했는지**: 팬덤/취미 기록은 SNS나 메신저, 갤러리 앱 등에 흩어지기 쉽고 시간이 지나면 다시 찾아보기 어렵습니다. 이런 기록을 카테고리별로 한 곳에 모아두고, 디지털에만 머무르지 않고 실물 책이라는 "간직할 수 있는 결과물"로 남길 수 있게 하면 좋겠다는 생각에서 출발했습니다. 기록(콘텐츠 제작) 서비스와 굿즈(실물 인쇄) 서비스를 하나의 흐름으로 이어 붙인 것이 이 아이디어의 핵심입니다.
- **사업적 가능성**: 온디맨드 포토북 인쇄 자체는 이미 수요가 검증된 시장이지만, 대부분 "사진 업로드 후 배치"에 초점이 맞춰져 있고 팬덤처럼 기록이 꾸준히 쌓이는 도메인에 특화된 곳은 많지 않습니다. 평소 기록 도구로 꾸준히 쓰이다가, 특정 시점(투어 종료, 연말, 팬클럽 기념일 등)에 자연스럽게 실물 주문으로 전환되는 구조라 재방문·전환 동기가 명확하다는 점에서 가능성이 있다고 봅니다. 카테고리를 팬덤 밖(여행, 육아, 반려동물 등)으로 넓히면 더 큰 기록형 커뮤니티로도 확장할 수 있습니다. 다만 현재는 결제, 실제 인쇄/배송 업체 연동, 다중 사용자 인증이 빠져 있어 실서비스로 가려면 이 부분이 먼저 채워져야 합니다.
- **더 시간이 있었다면 추가했을 기능**
  - 회원가입/로그인 기반의 다중 사용자 지원과 결제·배송 연동
  - 책 표지/내지 디자인 템플릿 선택 기능
  - 특정 기록이나 완성된 책을 다른 팬과 공유할 수 있는 기능
  - 태그·검색 기반 기록 필터링, "올해 몇 번 직관했는지" 같은 연간 요약 리포트
  - 업로드한 사진을 분석해 포토카드 위치나 책 페이지 배치를 자동으로 제안해주는 기능
